# HostelHub — Hostel & PG Booking Platform

A React + Vite frontend and Express REST API for hostel/PG discovery and booking. The project includes guest, hostel-owner, and admin dashboards, authentication, hostel listings, booking flows, analytics, and chat routes.

## Stack

- Frontend: React, Vite, React Router, Lucide
- Backend: Node.js, Express, JWT, bcryptjs
- Database: SQLite
- Frontend hosting: Vercel
- Backend hosting: Render (persistent disk required for SQLite)

## Important deployment note

**Do not deploy the Express server as a Vercel static frontend.** Vercel hosts the React/Vite frontend here; deploy the Express API separately on Render. SQLite needs persistent storage: the included `render.yaml` configures a Render disk mounted at `/var/data`. If you choose a hosting plan without persistent disks, migrate to a managed PostgreSQL database before going live.

## Deploy

### 1. Push the project to GitHub

Upload this repository to a GitHub repository. Keep `.env` files and secrets out of Git. `.env.example` files are templates only.

### 2. Deploy the API on Render

1. In Render, create a new Blueprint or Web Service from the GitHub repository.
2. If using the included `render.yaml`, Render configures `backend` as the root directory and requests a 1 GB persistent disk at `/var/data`.
3. Set `CORS_ORIGIN` to your exact Vercel site origin, for example `https://your-app.vercel.app` (no trailing slash). For preview deployments, add the relevant origins separated by commas.
4. Wait for the service to deploy, then verify `https://YOUR-API.onrender.com/health` returns JSON with `status: "ok"`.
5. The `JWT_SECRET` is generated by the Render blueprint. Do not replace it with a public or weak value.
6. **Seed carefully:** `npm run seed` recreates/populates demo data and may overwrite local demo state. Run it only against a fresh database, never casually against production user data. For a fresh deployment, use the Render Shell in the `backend` service and run `npm run seed` if demo listings/users are wanted.

### 3. Deploy the frontend on Vercel

1. Import the same GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`.
3. Framework preset: **Vite**. Build command: `npm run build`. Output directory: `dist`.
4. Add the environment variable:
   - `VITE_API_URL` = `https://YOUR-API.onrender.com/api`
5. Deploy. The included `frontend/vercel.json` sends client-side routes back to `index.html`.
6. If you change environment variables, redeploy the frontend.

### 4. Configure CORS

In Render, set `CORS_ORIGIN` to the production Vercel origin, e.g. `https://hostelhub.vercel.app`. If you use a custom domain, include that origin too, comma-separated. Do not include `/` paths.

## Local development

Prerequisite: Node.js 20+ recommended.

Terminal 1 — API:

```bash
cd backend
npm install
cp .env.example .env
# Edit JWT_SECRET in .env for local development if desired
npm run seed
npm run dev
```

Terminal 2 — frontend:

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Frontend normally runs at `http://localhost:5173`; API runs at `http://localhost:5000`.

## Deployment checklist

- [ ] GitHub repository created; no secrets committed
- [ ] Render API deployed and `/health` passes
- [ ] Persistent disk attached and `DB_PATH=/var/data/hostelhub.db`
- [ ] `JWT_SECRET` set by Render and kept private
- [ ] `CORS_ORIGIN` matches the Vercel production origin
- [ ] Vercel root directory is `frontend`
- [ ] Vercel `VITE_API_URL` points to the Render API `/api`
- [ ] Register/login, search, booking, owner dashboard, admin dashboard tested on deployed URLs
- [ ] Demo users/passwords removed or changed before production
- [ ] Payment flow reviewed: do not collect/store real card details without a compliant payment provider and server-side verification
- [ ] Production database backups, monitoring, rate limiting, and HTTPS verified

## Before real production use

This repository is a working project baseline, not a security/compliance certification. Before taking real bookings or payments, review authorization checks on every route, input validation, rate limiting, password reset/email verification, file/image upload storage, payment provider webhooks, booking concurrency/overbooking, database backups, privacy/terms, and logging of sensitive data. Never trust payment success reported by the browser alone.
